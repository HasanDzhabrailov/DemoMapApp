# MAP-023 - Decompose Android MapLibre renderer by responsibility without behavior change

## Context
`MapRenderer.android.kt` currently contains multiple Android-specific responsibilities in one file: Compose hosting, `MapView` lifecycle management, state restoration, style loading, viewport command execution, source/layer updates, and render application orchestration.

This ticket should improve renderer-side responsibility boundaries without changing behavior or moving business logic into the renderer.

## Goal
Refactor the Android renderer so that responsibilities are clearer and more isolated, while preserving behavior.

## Non-Goals
- No business logic migration into renderer
- No change to user-visible rendering behavior
- No redesign of map styles or overlays
- No broad rewrite of renderer APIs

## Functional Requirements
- Split the Android renderer into clearer responsibility groups
- Keep MapLibre integration Android-specific
- Keep renderer focused on rendering and Android integration only
- Preserve existing support for:
  - points
  - lines
  - polygons
  - current location marker
  - ruler line
  - drawing preview
  - camera observation
  - feature click observation
  - viewport commands
  - lifecycle/state restoration

## Acceptance Criteria
- [ ] Android renderer code is split by responsibility
- [ ] Rendering behavior remains unchanged
- [ ] Business logic is still absent from renderer
- [ ] MapLibre integration remains Android-specific
- [ ] Existing compile/test verification remains green

## Constraints
- Follow `AGENTS.md`
- Split by responsibility, not file size
- Preserve current renderer behavior
- Do not move feature logic into renderer

## Success Metrics
- Renderer files/classes are easier to describe with one responsibility each
- Future renderer changes are less risky
- The map feature architecture keeps a clear platform boundary
