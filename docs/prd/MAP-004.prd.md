# MAP-004 — Introduce minimal render adapter between feature state and map renderer

## Context
`MAP-003` isolates map rendering better than before, but the remaining coupling is in the renderer input contract.

The current renderer boundary still depends on feature-owned types such as `MapState` and `MapStyle`, which means the feature API still defines part of the render contract.

We need the smallest possible adapter seam that removes this ownership leak now without creating throwaway architecture that must be replaced later.

## Goal
Introduce a minimal, stable render adapter layer so `feature/map/api` owns screen state, `feature/map/render` owns renderer input, and Android-specific MapLibre rendering stays confined to `androidMain`.

## Non-Goals
- No business logic changes
- No navigation or Decompose redesign
- No new DI framework
- No broad module split
- No MapLibre feature expansion
- No new shared/core abstraction unless minimally required

## User Scenarios
- Scenario 1: A user opens the app and the map behaves exactly as before.
- Scenario 2: A developer can evolve feature state without making the renderer depend directly on feature API types.
- Scenario 3: A developer can add future render inputs such as camera or overlays by extending a render-owned model instead of rewriting the boundary.

## Acceptance Criteria
- [ ] `MapRenderer` no longer accepts `feature.map.api.MapState`
- [ ] Renderer input is owned by `feature.map.render`
- [ ] A minimal pure mapping step exists between feature state and renderer input
- [ ] `MapScreenContent` does not contain renderer-specific mapping logic beyond invoking the adapter
- [ ] Android MapLibre implementation remains only in `androidMain`
- [ ] Existing map behavior remains unchanged
- [ ] No business logic is added to render code or adapter code

## Constraints
- Follow `AGENTS.md`
- Keep the change minimal
- Respect KMP-first architecture
- Keep Compose UI-only
- Keep MapLibre as render layer only
- Preserve existing Decompose ownership

## Success Metrics
- Shared feature API no longer defines the renderer contract
- The adapter seam is small and explicit
- Future renderer inputs can be added by extending render-owned models
- Minimal relevant verification passes

## Open Questions
- Should feature-level `MapStyle` remain product-owned and map to a render-owned style enum, or should feature state expose a more generic semantic style id?
- Should the pure mapper live in `feature/map/impl` or as a non-Android adapter file inside `feature/map/render`?
