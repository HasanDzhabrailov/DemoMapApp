# MAP-008 — Add line and polygon drawing flow with preview and shared info window

## Context
The map feature already supports a minimal point flow: fixed center marker, create-point draft sheet, point rendering, and a shared info window for clicked points.

The next step is to add line and polygon creation by the same architectural rules: keep business state and drawing flow in shared code, keep MapLibre rendering and hit detection Android-specific, and avoid placing product logic inside the renderer.

The implementation must follow a lightweight MVI approach:
- `Model` is the single source of truth for screen state
- UI renders only from `Model`
- UI emits user intents as component events
- intent handling and state reduction stay outside composables

The requested UX uses a center-driven drawing flow similar to the provided examples:
- the user opens the center marker menu
- selects line or polygon creation
- enters a drawing mode
- the current vertex is always defined by the current camera center
- `+ позиция` adds the current center as a fixed vertex
- `Удалить` removes the last fixed vertex
- `Детали` opens a bottom sheet where the user enters the figure title and confirms creation

## Goal
Implement minimal end-to-end creation of lines and polygons with live drawing preview, title confirmation through a bottom sheet, map rendering with labels, and shared info window display on click, while keeping screen behavior aligned with lightweight MVI.

## Non-Goals
- No editing of existing points, lines, or polygons
- No deletion of already created map objects
- No details screen navigation
- No renderer business logic
- No MapLibre API leakage into shared business state
- No DI framework introduction
- No broad redesign outside the map business area
- No base-class hierarchy for map features or create flows unless it becomes strictly necessary
- No separate MVI framework introduction

## User Scenarios
- Scenario 1: A user opens the center marker menu and sees actions for point, line, and polygon creation.
- Scenario 2: A user selects line creation, enters drawing mode, adds positions from the current map center, and sees a live preview segment toward the current center.
- Scenario 3: A user selects polygon creation, enters drawing mode, adds positions from the current map center, and sees a live preview of the closing edges and captured area.
- Scenario 4: A user opens the details bottom sheet for a draft line or polygon, enters a title, and confirms creation.
- Scenario 5: A created line or polygon appears on the map with a text label similar to point labeling.
- Scenario 6: A user taps a created line or polygon and sees the same shared info window pattern used for points.
- Scenario 7: Existing point creation and point selection behavior remain unchanged.

## Acceptance Criteria
- [ ] `CenterMarkerMenuOverlay` shows `Создать точку`, `Создать линию`, and `Создать полигон`
- [ ] Selecting line or polygon creation switches the screen into a drawing mode owned by `MapScreenComponent.Model`
- [ ] In drawing mode, `+ позиция` adds the current `lastCameraSnapshot` center as a fixed vertex
- [ ] In drawing mode, `Удалить` removes the last fixed vertex
- [ ] In drawing mode, `Детали` opens a shared bottom sheet for title entry and explicit confirmation
- [ ] A line can be created only when at least 2 vertices are fixed
- [ ] A polygon can be created only when at least 3 vertices are fixed
- [ ] While drawing a line, after the first fixed vertex, a live preview line is rendered toward the current camera center
- [ ] While drawing a polygon, after enough vertices, a live preview shows closing edges and preview fill toward the current camera center
- [ ] Created lines and polygons are stored in minimal map feature state with explicit stable identity
- [ ] Created lines and polygons are rendered through a neutral render model
- [ ] Labels for lines and polygons are rendered on the map without coupling the renderer to product models directly
- [ ] Tapping a rendered line or polygon opens the same shared Compose info window pattern used for points
- [ ] The renderer exposes only neutral click outputs and does not depend on business models
- [ ] Android-only hit detection and MapLibre click integration for lines and polygons stay in `androidMain`
- [ ] No business logic is added to `MapRenderer` or `MapLibreCameraAdapter`
- [ ] Screen state is reduced through component-layer intent handling, not through composable-owned state
- [ ] Existing point flow and existing map behavior remain unchanged outside this minimal extension
- [ ] The implementation follows SOLID with focused responsibilities and minimal abstractions

## Constraints
- Follow `AGENTS.md`
- Keep the change minimal and within the map business area
- Keep Compose UI-only
- Keep MapLibre Android-specific
- Do not place business logic in renderer code
- Respect KMP-first architecture
- Keep source of truth for drawing mode, draft state, and selected info-window flow in `MapScreenComponent.Model`
- Follow lightweight MVI: intents in, model out, no business state in composables
- Prefer composition, interfaces, delegation, adapters, and small focused helpers over inheritance
- Avoid abstract base classes and unnecessary cross-feature generic hierarchies
- Avoid package churn and broad refactors

## Success Metrics
- Users can create a line from the current center-driven drawing flow
- Users can create a polygon from the current center-driven drawing flow
- Users can understand the captured path or area from live preview while drawing
- Users can tap created shapes and read their basic metadata
- Renderer remains thin, neutral, and platform-focused
- Point flow remains stable without regression
- Screen behavior remains predictable through single-source-of-truth state updates
- Minimal relevant verification passes

## Technical Notes
- Keep point flow intact and extend the architecture with minimal parallel shape support
- Prefer explicit `MapLine` and `MapPolygon` models over premature generic base hierarchies
- Keep preview computation outside Android-specific renderer code
- Keep click resolution in the component/use-case layer, not in renderer code
- Keep labels and info window content shared at the screen/component/UI level
- Keep draft state and draft transitions outside composables
- Keep MVI lightweight and local to this feature; do not introduce a new global framework
