# MAP-005 — Production-ready refactor of MapRenderer

## Context
Current `ru.tech.demomapapp.feature.map.render.MapRenderer` works, but the Android implementation mixes Compose orchestration, `MapView` lifecycle handling, and render model application in one place.

The initial refactor improved separation of responsibilities and removed redundant style reloads, but additional hardening is still required to align more closely with official MapLibre Android lifecycle guidance.

## Goal
Refactor `MapRenderer` so it is production-ready, lifecycle-safe, and aligned with SOLID, while preserving current behavior and keeping the public renderer contract unchanged.

## Non-Goals
- No business logic changes
- No feature API redesign
- No renderer contract redesign in common code
- No MapLibre feature expansion
- No navigation or Decompose changes
- No DI framework introduction
- No broad persistence or state restoration redesign outside the renderer boundary

## User Scenarios
- Scenario 1: A user opens the map screen and the map behaves exactly as before.
- Scenario 2: A developer can extend rendering logic without rewriting the full Android renderer.
- Scenario 3: A developer can reason independently about `MapView` creation, lifecycle binding, and render state application.
- Scenario 4: The renderer handles Android lifecycle transitions predictably and avoids unnecessary style reloads.

## Acceptance Criteria
- [ ] Public `MapRenderer` contract remains unchanged
- [ ] Android-specific MapLibre logic remains only in `androidMain`
- [ ] `setStyle(...)` is not triggered on every recomposition/update
- [ ] `MapView` lifecycle handling is predictable and safe
- [ ] Internal responsibilities are split into small focused units
- [ ] Existing rendering behavior remains unchanged
- [ ] Refactor follows SOLID without introducing unnecessary abstractions
- [ ] Renderer design accounts for official MapLibre lifecycle expectations
- [ ] `onLowMemory()` handling is addressed in the Android renderer lifecycle strategy
- [ ] Style application reacts only to relevant render model changes

## Constraints
- Follow `AGENTS.md`
- Keep the change minimal
- Keep Compose UI-only
- Keep MapLibre integration Android-specific
- Do not introduce business logic into render code
- Respect KMP-first architecture

## Success Metrics
- Android renderer is easier to read and extend
- Redundant renderer work is removed
- Lifecycle orchestration becomes explicit and stable
- Minimal relevant verification passes

## Notes
- Official MapLibre Android documentation requires forwarding `onCreate`, `onStart`, `onResume`, `onPause`, `onStop`, `onDestroy`, and `onLowMemory` from the parent lifecycle owner.
- `setStyle(...)` is asynchronous and should not be called unnecessarily.
- `onSaveInstanceState(...)` should be handled explicitly to preserve `MapView` internal state across recreation.
- The current screen assumes a single map instance, so renderer saved-state keys remain local to the Android renderer implementation.
