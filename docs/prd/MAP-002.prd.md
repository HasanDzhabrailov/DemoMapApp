# MAP-002 — Wrap MapLibre behind feature API facade with Android-only implementation

## Context
The project needs to isolate MapLibre behind an internal facade.
MapLibre must remain a render-only dependency.
All MapLibre platform-dependent code must stay in Android-specific code only.

The rest of the feature must depend on a project-owned API contract instead of direct MapLibre classes or Android-specific types.

## Goal
Introduce a facade contract in `feature/map/api` and provide its MapLibre-based implementation only in Android-specific code.

## Non-Goals
- No business logic inside the facade
- No MapLibre types in `commonMain`
- No Android framework types in shared business logic
- No direct MapLibre usage outside Android-specific code
- No new DI framework
- No Base classes
- No abstract base classes
- No broad refactoring beyond minimal integration changes

## User Scenarios
- Scenario 1: A user opens a screen with a map and sees the map rendered correctly.
- Scenario 2: A developer integrates map rendering through a stable internal API without direct dependency on MapLibre.
- Scenario 3: Shared feature code remains platform-agnostic.

## Acceptance Criteria
- [ ] A map facade contract is introduced in `feature/map/api`
- [ ] The facade contract contains render-level API only
- [ ] A MapLibre-based facade implementation exists only in Android-specific code
- [ ] No MapLibre classes are referenced from `commonMain`
- [ ] No Android-specific code leaks into business logic
- [ ] No business logic is placed in the facade or renderer
- [ ] Compose remains UI-only
- [ ] Side effects are not launched from the composable body
- [ ] Map rendering still works on Android after migration

## Constraints
- Follow `AGENTS.md`
- Keep the change minimal
- Respect KMP-first architecture
- Respect `feature/api/impl`
- Keep platform-specific code in `androidMain/android`
- Keep MapLibre as render layer only

## Success Metrics
- Map rendering works on Android
- Shared code has no direct dependency on MapLibre
- The feature depends on internal map API only
- Verification commands pass

## Open Questions
- Should the facade contract describe only render input, or render input plus UI callbacks?
- Should Android-specific implementation be placed in `composeApp/androidMain` or Android-specific part of `feature/map/impl`?
