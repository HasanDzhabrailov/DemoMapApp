# MAP-013 - Introduce MVIKotlin store skeleton for MapScreen without behavior change

## Context
The current map feature already uses a single screen model and event-style callbacks through Decompose, but the main logic is centralized in `DefaultMapScreenComponent`. This creates a fake-MVI architecture where state, transitions, and side effects are mixed in one class.

Before migrating individual flows, the feature needs a minimal MVIKotlin-compatible skeleton that keeps Decompose integration and preserves current behavior.

## Goal
Introduce a store-oriented architecture skeleton for `MapScreen` that:
- keeps Decompose as the screen/component boundary
- introduces an internal Store contract for the map screen
- does not change user-visible behavior
- does not yet migrate business logic out of the existing component in a risky way

## Non-Goals
- No full migration of screen logic to MVIKotlin yet
- No reducer/executor split yet beyond the minimum skeleton
- No renderer refactor
- No UI redesign
- No behavior changes in map, GPS, ruler, drawing, or overlays

## Functional Requirements
- Add MVIKotlin dependency/dependencies required for a Decompose-integrated Store setup
- Introduce internal map store package/structure for the map feature
- Define initial internal Store factory and Store interface for `MapScreen`
- Keep `DefaultMapScreenComponent` as the public Decompose component implementation
- Keep all existing `onXxx` APIs on `MapScreenComponent`
- Preserve the existing `model` contract for UI usage during this ticket
- Ensure the new store skeleton can be used incrementally in later tickets

## Acceptance Criteria
- [ ] MVIKotlin dependency is available to the map feature module
- [ ] A dedicated internal store package exists for map feature screen logic
- [ ] `MapScreen` has an internal Store contract/factory with minimal initial wiring
- [ ] `DefaultMapScreenComponent` remains the Decompose-facing entry point
- [ ] Existing UI behavior remains unchanged
- [ ] Existing tests continue to pass without semantic changes
- [ ] The change is incremental and ready for further migration tickets

## Constraints
- Follow `AGENTS.md`
- Keep changes minimal and architecture-oriented
- Preserve Decompose integration
- Do not rewrite the feature
- Do not expand scope outside the map business area

## Success Metrics
- The repository has a safe MVIKotlin entry point for `MapScreen`
- The component can start delegating to Store in later tickets
- No behavior regression is introduced
