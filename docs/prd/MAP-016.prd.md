# MAP-016 - Move MapScreen side effects into Executor and formalize one-time outputs

## Context
`MAP-015` establishes a pure reducer for simple state transitions. The next step is to isolate side effects from state mutation by introducing an Executor and formalizing one-time outputs.

The current map screen uses ad hoc state-carried effects such as `pendingLocationRequest` and `pendingViewportCommand`. This ticket should begin migrating those responsibilities toward MVIKotlin executor/label structure.

## Goal
Introduce an Executor for `MapScreen` and move side-effect responsibilities out of direct component logic, while preserving behavior.

## Non-Goals
- No full migration of every business flow
- No renderer redesign
- No public API removal yet
- No broad rewrite of location/render integrations

## Functional Requirements
- Introduce `Executor` for `MapScreen`
- Keep `Reducer` pure
- Migrate one-time side-effect responsibilities into executor-oriented handling
- Formalize one-time outputs using Store labels and/or a controlled transitional pattern
- Preserve current GPS and viewport behavior

## Scope for This Ticket
Preferred first side effects:
- location request triggering
- location result handling entry path
- viewport command emission path
- one-time consume semantics now represented by:
  - `pendingLocationRequest`
  - `pendingViewportCommand`

## Acceptance Criteria
- [ ] `MapScreen` Store has an executor
- [ ] Reducer remains pure
- [ ] Side effects are no longer initiated directly from reducer logic
- [ ] One-time outputs have explicit architecture ownership
- [ ] Existing GPS and viewport flows preserve behavior
- [ ] Existing UI integrations continue to work during migration

## Constraints
- Follow `AGENTS.md`
- Keep migration incremental
- Do not break current location permission flow
- Do not move platform implementation into common business logic

## Success Metrics
- Side effects become isolated
- The component no longer acts as the primary side-effect engine for migrated flows
- The architecture supports later migration of ruler and drawing workflows
