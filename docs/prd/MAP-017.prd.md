# MAP-017 - Migrate ruler flow to Store-first MVIKotlin architecture

## Context
The ruler flow is a strong candidate for Store-first migration because it already has explicit state, calculation helpers, and clear behavior rules. At the moment, ruler activation, fallback location creation, and measurement recalculation are still orchestrated inside `DefaultMapScreenComponent`.

This ticket should move ruler behavior toward explicit MVIKotlin ownership while preserving the current user-visible behavior delivered in `MAP-012`.

## Goal
Migrate the ruler flow so that:
- Store becomes the center of ruler logic
- reducer owns pure ruler state transitions
- executor owns ruler side effects and orchestration
- Decompose component becomes thinner
- behavior remains unchanged

## Non-Goals
- No redesign of ruler UI
- No renderer redesign beyond the minimal integration required
- No migration of all map flows in this ticket
- No broad API cleanup yet

## Functional Requirements
- Represent ruler interactions through explicit Store intents
- Move ruler enable/disable transitions into reducer-driven state changes
- Move fallback manual origin creation and recalculation orchestration into executor-driven logic where needed
- Preserve the existing ruler origin priority:
  - GPS marker
  - manual placeholder marker
  - fallback manual placeholder from camera snapshot
  - deferred fallback until first snapshot
- Preserve ruler recalculation behavior on:
  - camera updates
  - GPS resolution
  - manual location updates when GPS is not active
- Preserve dedicated ruler render state separate from user-created lines
- Preserve dedicated ruler info window behavior

## Acceptance Criteria
- [ ] Ruler flow is driven through explicit Store intents
- [ ] Pure ruler state transitions are handled by reducer
- [ ] Side-effect/orchestration parts of ruler flow are owned by executor
- [ ] Existing ruler behavior from `MAP-012` remains unchanged
- [ ] Ruler render state remains separate from persistent map feature data
- [ ] Tests continue to cover ruler scenarios

## Constraints
- Follow `AGENTS.md`
- Keep business calculations in shared code
- Keep renderer Android-specific
- Do not place business logic in renderer code
- Keep migration incremental

## Success Metrics
- Ruler logic no longer depends primarily on component-local orchestration
- Store is the clear center of ruler behavior
- Future ruler enhancements can be added without growing the component
