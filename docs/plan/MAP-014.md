# Plan - MAP-014

## Summary
Create explicit Store contracts for map screen state, intents, and labels. Keep `MapScreenComponent` as a compatibility wrapper while the new contracts become the architectural center.

## Affected Modules
- `feature/map/api`
- `feature/map/impl`
- internal map store package introduced in `MAP-013`

## File-Level Plan
- Add/expand internal files such as:
  - `feature/map/impl/store/MapStore.kt`
  - `feature/map/impl/store/MapStoreIntent.kt`
  - `feature/map/impl/store/MapStoreState.kt`
  - `feature/map/impl/store/MapStoreLabel.kt`
- Add temporary mapping from current component callbacks to Store intents
- Add temporary mapping from Store state to current `MapScreenComponent.Model` if both must coexist during migration

## Intent Plan
Group current callbacks by responsibility instead of keeping them conceptually flat:
- map camera / viewport intents
- tools/menu intents
- location intents
- ruler intents
- center marker intents
- create-point intents
- drawing intents
- feature selection intents

## State Plan
Store state should become the source of truth for:
- map feature data
- camera snapshot
- overlays/sheets visibility
- location mode and marker
- ruler state
- drawing state
- selected feature state
- one-time command placeholders until later executor/label migration

## Label Plan
Reserve labels for future one-time outputs such as:
- viewport side effects
- location side effects
- transient notifications if needed later

## Migration Strategy
1. Enumerate all existing callback responsibilities
2. Define Store intents around responsibility groups
3. Define Store state around stable screen ownership
4. Define labels for one-time outputs
5. Add wrapper mapping from component methods to `store.accept(intent)`
6. Keep current UI contract stable

## Verification
- `./gradlew :composeApp:compileDebugKotlinAndroid`
- `./gradlew :composeApp:compileKotlinJvm`
- `./gradlew :composeApp:test`

## Risks and Mitigations
- Risk: intent contract mirrors current `onXxx` methods too literally
  - Mitigation: group by responsibility, but keep migration realistic
- Risk: state duplicates current component model awkwardly
  - Mitigation: accept temporary duplication only where needed to keep migration safe
- Risk: labels are underused initially
  - Mitigation: define them deliberately for future side-effect migration

## Task Breakdown
1. Inventory current callback surface
2. Define `MapStore.Intent`
3. Define `MapStore.State`
4. Define `MapStore.Label`
5. Add wrapper mapping from component methods to intents
6. Keep current screen behavior unchanged
7. Run minimal verification
