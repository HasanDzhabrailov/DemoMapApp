# Plan - MAP-011

## Summary
Add real one-shot current-location behavior and a separate always-visible left-side my-location button, while preserving MAP-010 menu, zoom, compass, center-marker creation flows, and shared feature info behavior.

## Affected Modules
- `feature/map/api`
- `feature/map/impl`
- `feature/map/ui`
- `feature/map/render`
- `androidMain` map/location integration
- Android manifest
- Android build config only if a new location dependency is required

## File-Level Plan
- Extend `MapScreenComponent` with explicit my-location mode/state and a one-shot platform request effect
- Replace placeholder GPS toggle behavior in `DefaultMapScreenComponent` with a small shared state machine
- Add a separate shared my-location button overlay on the left side
- Keep existing settings menu and zoom overlay structure intact
- Extend `MapRenderModel` with a dedicated optional current-location marker separate from user-created points
- Replace the zoom-only viewport enum with a payload-capable viewport command model
- Update `MapScreenContent` to wire my-location UI and bind the platform location effect
- Add Android-only permission/location effect execution outside renderer business logic
- Update `MapRenderer.android.kt` to render the dedicated location marker and execute move-camera commands
- Keep the location marker out of feature click handling
- Update JVM renderer stub to accept the new API surface
- Add Android location permissions to the manifest
- Add dependency only if the chosen Android location backend requires it
- Add and update tests for GPS, manual placeholder mode, and regressions

## Architecture Notes
- `MapScreenComponent.Model` remains the owner of screen state
- Compose remains UI-only; composables emit intents and observe consumable effects
- Android permission and location APIs stay in `androidMain`
- Renderer remains responsible only for drawing and camera execution
- Current location is transient screen/render state, not part of `MapState`
- Manual placeholder mode is explicit and separate from GPS mode
- The current-location marker uses a dedicated render path so it does not behave like a user-created point
- The new left-side my-location button should be placed above the existing settings button to avoid MAP-010 zoom/compass collisions
- The ticket does not force a long-term Android location backend decision; it only requires a minimal one-shot implementation behind a narrow boundary

## Proposed Shared Models
- `enum class MyLocationMode { OFF, MANUAL_PLACEHOLDER, GPS }`
- `data class MapLocationMarker(val latitude: Double, val longitude: Double, val isPlaceholder: Boolean)`
- `sealed interface MapLocationRequest`
- `data object EnableGpsLocationRequest : MapLocationRequest`
- `data object RecenterToGpsLocationRequest : MapLocationRequest`
- `sealed interface LocationRequestResult`
- `data object PermissionDenied : LocationRequestResult`
- `data object LocationUnavailable : LocationRequestResult`
- `data class LocationResolved(val latitude: Double, val longitude: Double) : LocationRequestResult`

## Proposed State Additions
- `myLocationMode: MyLocationMode = OFF`
- `currentLocationMarker: MapLocationMarker? = null`
- `pendingLocationRequest: MapLocationRequest? = null`

## Proposed State Removal/Refinement
- Replace `isGpsEnabled` with `myLocationMode`
- Keep `pendingViewportCommand`, but evolve it into a payload-capable command model

## Proposed Intents
- `onGpsToggle()`
- `onMyLocationClick()`
- `onLocationRequestConsumed()`
- `onLocationResult(result: LocationRequestResult)`
- `onViewportCommandConsumed()`

## Proposed Viewport Commands
- `ZoomIn`
- `ZoomOut`
- `MoveTo(latitude, longitude)`

## State Machine Rules
- Default state:
  - `myLocationMode = OFF`
  - `currentLocationMarker = null`

- `onGpsToggle()` when mode is `OFF` or `MANUAL_PLACEHOLDER`:
  - enqueue `EnableGpsLocationRequest`
  - do not switch to `GPS` yet
  - do not show marker yet

- `onGpsToggle()` when mode is `GPS`:
  - switch mode to `OFF`
  - clear `currentLocationMarker`
  - clear `pendingLocationRequest`

- `onMyLocationClick()` when mode is `GPS`:
  - enqueue `RecenterToGpsLocationRequest`

- `onMyLocationClick()` when mode is `OFF` or `MANUAL_PLACEHOLDER`:
  - if `lastCameraSnapshot == null`, do nothing
  - else switch mode to `MANUAL_PLACEHOLDER`
  - set `currentLocationMarker` from current map center
  - do not enqueue permission or GPS request

- `onLocationResult(PermissionDenied)`:
  - switch mode to `OFF`
  - clear `currentLocationMarker`
  - clear pending request

- `onLocationResult(LocationUnavailable)`:
  - switch mode to `OFF`
  - clear `currentLocationMarker`
  - clear pending request

- `onLocationResult(LocationResolved)` after any GPS request:
  - switch mode to `GPS`
  - set `currentLocationMarker`
  - clear manual placeholder semantics
  - enqueue `MoveTo(latitude, longitude)`

## Android Location Execution
Preferred structure:
- Add an Android-only location effect binder used from `MapScreenContent`
- Binder responsibilities:
  - inspect `pendingLocationRequest`
  - check/request permission
  - resolve current location once
  - report aggregated result back through `onLocationResult(...)`
  - call `onLocationRequestConsumed()` when the request is taken

Important constraints:
- No permission logic in shared component
- No permission logic in renderer
- No location lookup in composable body
- No continuous listeners
- No background/service orchestration

## Android Backend Decision
- Keep the backend behind a narrow Android-only boundary
- Accept either a minimal `LocationManager`-based one-shot implementation or a dependency-backed provider if it is clearly justified during implementation
- Do not expose backend-specific APIs to common code
- Do not block the ticket on choosing a future long-term provider strategy

## SOLID Check
- `SRP`: screen component owns state machine, Android binder owns permission/location bridge, renderer owns drawing/camera
- `OCP`: location behavior extends state/effect/command models without rewriting unrelated map flows
- `LSP`: no inheritance-heavy design is introduced
- `ISP`: platform interaction is exposed through narrow screen-level intents/results
- `DIP`: shared logic depends on request/result abstractions, not Android APIs

## AGENTS.md Check
- KMP-first preserved
- Compose remains UI-only
- Android-specific code stays in `androidMain`
- MapLibre remains rendering/camera only
- Business logic stays out of renderer
- Scope stays inside current map business area
- Change remains minimal and incremental

## Risks and Mitigations
- Permission flow may repeat on recomposition
  - Mitigation: consumable `pendingLocationRequest` plus explicit consume callback
- Current-location marker may leak into user-created feature behavior
  - Mitigation: dedicated render model and dedicated renderer layer outside feature click queries
- Manual placeholder mode may run before first camera snapshot exists
  - Mitigation: do nothing when `lastCameraSnapshot == null`
- New left-side button may conflict with existing overlays
  - Mitigation: place it above the existing settings button and leave right-side controls untouched
- Android backend choice may add implementation uncertainty
  - Mitigation: keep backend behind an Android-only boundary and defer concrete provider choice to implementation with minimal impact on common code
