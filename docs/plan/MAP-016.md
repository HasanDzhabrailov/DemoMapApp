# Plan - MAP-016

## Summary
Introduce the map screen executor and migrate the first side-effect-heavy flows out of direct component logic. Preserve current behavior and keep Android-specific implementation out of shared business logic.

## Affected Modules
- internal map store package
- `feature/map/impl`
- `feature/map/ui`
- possibly Android location effect integration depending on transitional approach

## File-Level Plan
- Add executor-related files such as:
  - `feature/map/impl/store/MapStoreExecutor.kt`
- Add label handling for one-time outputs
- Update component wrapper to observe store labels and bridge them to current UI integration if necessary
- Keep `MapLocationEffectBinder` Android-specific
- Keep renderer Android-specific

## Side-Effect Ownership Plan
Executor should own:
- requesting GPS/location side-effect outputs
- responding to location results from external platform callback path
- emitting viewport one-time outputs
- invoking use cases or imperative helpers where the migrated flow requires it

Reducer should own:
- pure state transitions only

## Transitional Strategy
- Preserve current UI-facing integration points while moving architectural ownership
- If the UI still needs `request`/`command` props temporarily, derive them from store-driven labels through a controlled adapter path
- Avoid a big-bang replacement of current one-shot handling

## Migration Steps
1. Add executor
2. Identify first side-effect intents and results
3. Move location request initiation to executor flow
4. Move viewport command emission ownership to executor/label flow
5. Keep reducer pure
6. Keep component as Decompose wrapper and bridge
7. Verify consume-once semantics remain correct

## Verification
- `./gradlew :composeApp:compileDebugKotlinAndroid`
- `./gradlew :composeApp:compileKotlinJvm`
- `./gradlew :composeApp:test`

## Risks and Mitigations
- Risk: duplicate one-shot events during transition
  - Mitigation: define a single architecture owner per migrated effect
- Risk: Compose/platform binders consume outputs incorrectly
  - Mitigation: keep transitional adapter path explicit and test consume semantics
- Risk: GPS behavior regression
  - Mitigation: migrate only location/viewport effect ownership, not all location policy at once

## Task Breakdown
1. Add executor
2. Define effect-related labels/results
3. Move location request initiation to executor ownership
4. Move viewport command emission to executor ownership
5. Bridge store outputs to current UI/platform integration
6. Keep reducer pure
7. Run minimal verification
