# Plan - MAP-030

## Summary
Implement map layer management from the map settings menu with a tile-source conversion layer that adapts catalog entries into renderer-compatible descriptors without breaking the current single-style map flow.

## Affected Modules
- `composeApp/src/commonMain/kotlin/ru/tech/demomapapp/feature/map/api`
- `composeApp/src/commonMain/kotlin/ru/tech/demomapapp/feature/map/impl`
- `composeApp/src/commonMain/kotlin/ru/tech/demomapapp/feature/map/impl/store`
- `composeApp/src/commonMain/kotlin/ru/tech/demomapapp/feature/map/ui`
- `composeApp/src/commonMain/kotlin/ru/tech/demomapapp/feature/map/render`
- `composeApp/src/androidMain/kotlin/ru/tech/demomapapp/feature/map/render`
- `composeApp/src/commonTest/kotlin/ru/tech/demomapapp/feature/map`
- `composeApp/src/androidTest` if Android renderer coverage is needed

## Implementation Notes

### 1. Add product models in commonMain
Introduce common models for:
- available map catalog item
- loaded map layer entry
- layer type: `BASE` / `OVERLAY`
- layer order
- layer opacity
- source reference id
- selected layer action target
- pending confirmation target

These models must remain product-level and renderer-agnostic.

### 2. Extend feature state
Extend:
- `MapState`
- `MapScreenComponent.Model`
- `MapStore.State`

Add state for:
- available maps UI visibility
- maps on screen UI visibility
- confirmation dialog visibility
- opacity editor visibility
- active base layer
- overlay layer list
- selected layer action state

### 3. Add MVI flow
Add new store intents/messages for:
- open/close available maps
- select available map
- confirm add map
- cancel add map
- open/close maps on screen
- open/close layer actions
- move layer up
- move layer down
- open opacity editor
- apply opacity
- remove layer

Rules:
- reducer remains pure
- executor performs orchestration/validation only
- component remains a navigation/lifecycle bridge only

### 4. Add static tile-based catalog
Create a static first-version catalog with:
- DEM base style
- OpenStreetMap raster tile source
- Google raster tile template
- Yandex raster tile template

The catalog must live in `commonMain` as product data, while renderer-specific details are produced later by conversion.

### 5. Add source conversion boundary
Introduce a converter so current render flow does not break.

Suggested boundary:

Common models:
- `MapLayerCatalogItem`
- `MapLayerSourceRef`
- `MapLayerEntry`

Android models:
- `AndroidMapLayerDescriptor`
- `MapLayerSourceConverter`

`MapLayerSourceRef` should support:
- `BaseStyle`
- `RasterTileTemplate`

`AndroidMapLayerDescriptor` should support:
- style url for base style
- raster source id
- raster layer id
- tile template url
- tile size
- min zoom
- max zoom
- attribution
- default opacity

Purpose:
- preserve `MapState -> MapRenderModel`
- avoid provider logic in reducer/UI
- keep DEM/current default path backward compatible

### 6. Extend render model
Extend render model with:
- active base descriptor
- ordered overlay descriptors

Keep current geometry rendering unchanged:
- points
- lines
- polygons
- current location
- ruler
- drawing preview

### 7. Implement UI in commonMain
Add:
- available maps list UI
- confirm-add dialog
- maps-on-screen bottom sheet
- per-layer actions dialog/sheet
- opacity slider sheet

Use existing Compose patterns already present in map feature.

### 8. Implement Android renderer changes
Implement support for:
- applying base style descriptors
- applying raster tile layers
- removing raster tile layers
- reordering raster tile layers
- updating raster tile layer opacity

Keep all MapLibre operations Android-specific.

### 9. Backward compatibility strategy
- Keep current DEM/default map working through existing base style path
- Treat new sources as normalized descriptors
- If a source cannot be converted, fail safely and keep current map state stable

### 10. Verification
Run only relevant commands:
- `./gradlew :composeApp:test`
- `./gradlew :composeApp:compileKotlinJvm`
- `./gradlew :composeApp:compileDebugKotlinAndroid`

## Risks and Mitigations
- Risk: current renderer assumes one style only
  - Mitigation: keep base style path intact and add overlay descriptors incrementally
- Risk: Google/Yandex tile templates may be restricted
  - Mitigation: keep them isolated in catalog/converter and validate release suitability separately
- Risk: renderer details leak into common code
  - Mitigation: strict separation between source refs and Android descriptors
- Risk: layer ordering conflicts with app-owned map objects
  - Mitigation: apply external tile layers below app geometry layers
