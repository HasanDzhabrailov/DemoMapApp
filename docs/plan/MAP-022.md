# Plan - MAP-022

## Summary
Separate helper and Store-facing models from `MapScreenComponent` nested DTOs. This ticket is about contract ownership and responsibility boundaries, not behavior changes.

## Affected Modules
- `feature/map/api`
- `feature/map/impl`
- internal map store package
- `feature/map/ui` only if type references need updating
- `feature/map/render` only if mapping contracts need updating

## Likely Targets
- shape drawing draft models currently tied to `MapScreenComponent`
- feature info window models currently tied to `MapScreenComponent`
- feature type / click bridge types if component ownership is unnecessary
- any helper that imports component types only for data transport

## File-Level Plan
- Introduce dedicated Store/feature model files where justified
- Update helpers such as:
  - `ShapeDrawingDraftUpdater`
  - `MapFeatureSelectionResolver`
  - `MapFeatureInfoWindowStateMapper`
  - `MapRenderModelMapper`
- Keep `MapScreenComponent` focused on screen/component contract only
- Avoid moving renderer-specific models into the wrong layer

## Responsibility Target
- Component contract should expose screen-facing API only
- Store models should belong to Store/feature packages
- Renderer models should belong to renderer packages
- Helpers should depend on the narrowest justified model set

## Migration Strategy
1. Inventory all helper/model dependencies on `MapScreenComponent`
2. Identify unnecessary ownership coupling
3. Introduce dedicated models only where they reduce coupling clearly
4. Update helpers and adapters to use the new models
5. Keep behavior and public UI contract stable

## Verification
- `./gradlew :composeApp:compileDebugKotlinAndroid`
- `./gradlew :composeApp:compileKotlinJvm`
- `./gradlew :composeApp:test`

## Risks and Mitigations
- Risk: over-splitting simple DTOs into too many files
  - Mitigation: introduce only responsibility-justified models
- Risk: accidental package churn without clear benefit
  - Mitigation: keep the change focused on real coupling problems
- Risk: UI/render adapters break due to type migration
  - Mitigation: preserve adapter paths and verify all affected flows

## Task Breakdown
1. Audit all `MapScreenComponent` nested model usages
2. Identify helpers coupled to component-owned models
3. Introduce dedicated Store/feature models where justified
4. Update helpers and mappers to depend on new models
5. Keep behavior unchanged
6. Run minimal verification
