# Plan - MAP-013

## Summary
Introduce the minimum MVIKotlin store skeleton behind `MapScreen` while preserving the existing Decompose component API and behavior. This ticket creates the architectural seam for later migration.

## Affected Modules
- `composeApp`
- `feature/map/api`
- `feature/map/impl`

## File-Level Plan
- Add MVIKotlin dependency in `composeApp/build.gradle.kts`
- Introduce internal package for map store, for example:
  - `feature/map/impl/store/MapStore.kt`
  - `feature/map/impl/store/MapStoreFactory.kt`
- Keep `MapScreenComponent` unchanged in this ticket
- Keep `MapScreenContent` unchanged in this ticket
- Keep `DefaultMapScreenComponent` as the Decompose-facing component, but prepare it to hold/create the store
- If needed, add adapter/wrapper code so current component model can remain the source for UI

## Architecture Notes
- Decompose component remains responsible for lifecycle and store holding
- Store introduction is internal first, not a public API break
- This ticket intentionally keeps old callback methods and current model contract
- No business logic migration is required yet
- No reducer/executor complexity should be introduced unless needed to establish the skeleton

## Proposed Internal Structure
- `MapStore.Intent`
- `MapStore.State`
- `MapStore.Label`
- `MapStoreFactory`
- optional temporary adapter between old `MapScreenComponent.Model` and store state

## Migration Strategy
1. Add MVIKotlin dependencies
2. Create internal Store contract and factory
3. Create minimal initial state mirroring current screen needs at a high level
4. Instantiate/hold store inside `DefaultMapScreenComponent`
5. Keep current callbacks and behavior intact
6. Keep component model usable for current UI
7. Verify no user-visible behavior changes

## Verification
- `./gradlew :composeApp:compileDebugKotlinAndroid`
- `./gradlew :composeApp:compileKotlinJvm`
- `./gradlew :composeApp:test`

## Risks and Mitigations
- Risk: introducing Store without usage creates dead scaffolding
  - Mitigation: wire it into component ownership and name it consistently for later tickets
- Risk: dependency/setup mismatch in KMP
  - Mitigation: keep the first ticket limited to minimal compile-safe setup
- Risk: accidental behavior drift
  - Mitigation: do not migrate flow logic yet

## Task Breakdown
1. Add MVIKotlin library support to the module
2. Introduce internal map store contract
3. Introduce internal map store factory
4. Create minimal state/intent/label placeholders
5. Wire store creation into `DefaultMapScreenComponent`
6. Preserve existing component API and behavior
7. Run minimal verification
