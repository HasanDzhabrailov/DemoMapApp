# Plan — MAP-001

## Summary
Add MapLibre rendering on Android through `AndroidView`, keep all platform-specific integration in Android-specific code, and ensure map code stays a pure render layer without business logic.

## Affected Modules
- `composeApp/commonMain`: define shared UI contract only if needed
- `composeApp/androidMain`: place `AndroidView` and MapLibre integration here
- `core/common`: no change expected
- `core/ui`: only if a small reusable UI model or contract is needed
- `feature/map/api`: optionally expose UI state and events contract
- `feature/map/impl`: keep screen/component state outside the renderer
- `root/api`: no change expected
- `root/impl`: no change expected
- `root/ui`: only if navigation wiring is needed

## Implementation Notes
- Add Android-specific map renderer based on `AndroidView`
- Keep MapLibre setup and lifecycle handling in Android-specific code
- Pass render data into the map renderer from outside
- Keep map interactions exposed as UI events only
- Do not place business rules, orchestration, or decision-making inside map rendering code
- Avoid broad refactoring

## Risks
- Map lifecycle handling inside `AndroidView` may require careful cleanup
- Existing UI may mix rendering concerns with state ownership
- Android-specific dependencies may accidentally leak into shared code if boundaries are not enforced

## Verification
- `./gradlew ktlintCheck`
- `./gradlew detekt`
- `./gradlew test`

## Task Breakdown
1. Identify the target screen/module for map rendering
2. Add Android-specific MapLibre renderer using `AndroidView`
3. Keep renderer API UI-focused and free from business logic
4. Ensure shared code does not depend on Android MapLibre APIs
5. Wire renderer into the screen with state provided from outside
6. Run verification
