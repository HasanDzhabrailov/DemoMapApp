# Plan — MAP-008

## Summary
Extend the current point-based map flow with center-driven line and polygon drawing, shared draft state, live preview rendering, title confirmation through a bottom sheet, neutral feature selection, and Android-only rendering and hit detection for the new geometries, while keeping responsibilities small, aligned with SOLID, and structured as lightweight MVI.

## Affected Modules
- `feature/map/api`: add line/polygon business models, extend screen contract, and expand main screen state
- `feature/map/impl`: add intent handling, drawing orchestration, shape creation use cases, draft update helpers, selection resolution, and presentation mapping
- `feature/map/ui`: extend center menu, add drawing controls, and add a shared shape details bottom sheet
- `feature/map/render` common: extend neutral render model for lines, polygons, preview, and feature clicks
- `feature/map/render` android actual: render lines, polygons, and drawing preview; add Android-only hit detection for shapes

## File-Level Plan
- Keep `MapScreenComponent.Model` as the single source of truth for screen state
- Extend `MapScreenComponent.Model` with drawing-mode state, shape draft state, and bottom-sheet visibility for line and polygon creation
- Keep point draft flow intact and separate from shape drawing flow
- Add `MapVertex`, `MapLine`, and `MapPolygon` business models with explicit ids, titles, created timestamps, and vertices
- Extend `MapState` with minimal in-memory collections for lines and polygons
- Add shape-specific use cases for draft-to-business conversion and validation
- Add a focused draft updater helper for append/remove operations in drawing mode
- Add a focused preview mapper/helper that converts active draft state and current center into neutral preview geometry
- Add neutral renderer models for rendered lines, rendered polygons, and active drawing preview
- Update `MapRenderModelMapper` to map business state and active draft state to neutral renderer input
- Add shared Compose drawing controls overlay for `Удалить`, `+ позиция`, and `Детали`
- Add shared Compose bottom sheet for line/polygon title entry and confirmation
- Generalize point-only click output into a neutral feature click seam with minimal scope
- Resolve clicked shape back to business state in component layer only

## Implementation Notes
- Keep `MapRenderer` render-only
- Keep `MapLibreCameraAdapter` camera observation-only
- Keep Android-specific map click integration and geometry hit detection in `androidMain`
- Keep business state, UI state, and renderer contract separate
- Use explicit stable identity for shapes so renderer selection does not depend on derived geometry keys
- Use `lastCameraSnapshot` as the source of the current drawing position
- Compute preview geometry in shared/component/mapper flow instead of Android renderer logic
- Render line and polygon labels through the neutral render model
- Keep the info-window UI in shared Compose above the map
- Preserve existing point rendering and selection behavior unchanged
- Prefer small focused collaborators over expanding `DefaultMapScreenComponent` with geometry and validation details
- Avoid base classes and avoid introducing a broad generic geo-object architecture in this ticket
- Keep MVI lightweight:
  - component methods represent intents
  - model represents view state
  - state transitions stay in component/reducer-style helpers
  - composables only render and emit events

- `RenderMapPolygon`

## Risks
- `DefaultMapScreenComponent` could become overloaded if drawing logic, preview logic, and selection logic are all kept inline
- Renderer click handling could accidentally grow product semantics if feature selection is not kept neutral
- Preview rendering for polygons could drift from business expectations if closing geometry is computed in the wrong layer
- Shape hit detection may be less reliable than point hit detection if layer ids, tolerance, or anchor strategy are not explicit
- Existing point flow could regress if line and polygon support is introduced through a broad shared refactor
- MVI could become ceremonial if too many abstractions are added for a single screen

## Risk Mitigation
- Keep point flow intact and add shape flow in parallel instead of rewriting existing point architecture
- Move draft validation, vertex update rules, and preview building into small focused helpers or use cases
- Keep renderer input fully neutral and precomputed before reaching Android-specific code
- Use explicit source ids, layer ids, feature ids, and click tolerance values for each geometry type
- Keep all draft state in `MapScreenComponent.Model` and keep composables stateless with event callbacks only
- Add regression tests for point flow before or alongside shape-flow tests
- Introduce only the minimum neutral feature click seam needed for shared info-window behavior
- Keep MVI local and pragmatic; do not introduce a separate store framework or excessive intent/result layers
