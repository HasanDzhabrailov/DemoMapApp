# Plan — MAP-005

## Summary
Refactor the Android `MapRenderer` into a thin composable orchestrator with focused internal responsibilities for `MapView` creation, lifecycle binding, render model application, and style resolution, then harden the lifecycle integration to better reflect official MapLibre guidance.

## Affected Modules
- `feature/map/render` common expect: no public API change expected
- `feature/map/render` android actual: primary refactor target
- `feature/map/render` jvm actual: keep contract aligned, minimal cleanup only if needed
- `feature/map/ui`: no behavioral change expected

## Implementation Notes
- Keep `MapRenderer(model, modifier)` unchanged
- Keep Android-specific MapLibre code only in `androidMain`
- Maintain a small internal holder for Android renderer state
- Separate `MapView` ownership from lifecycle binding
- Separate render model application from `AndroidView` factory/update
- Keep style application idempotent
- Scope render updates only to fields that actually affect the applied map state
- Keep `RenderMapStyle -> style URL` mapping in Android code only
- Add an explicit strategy for `onLowMemory()`
- Add minimal `onSaveInstanceState(...)` support through `SavedStateRegistryOwner` without changing the public renderer API
- Avoid broad package churn or unnecessary abstractions

## Risks
- Incorrect lifecycle decomposition may cause duplicate start/stop calls
- Over-abstraction may expand scope beyond the ticket
- Style application changes may accidentally alter current rendering behavior
- Incomplete lifecycle forwarding may still diverge from MapLibre expectations under memory pressure

## Task Breakdown
1. Re-check current Android renderer against official MapLibre lifecycle documentation
2. Keep `MapRenderer` as thin orchestration only

4. Ensure style application is idempotent and keyed only by relevant render fields

7. Keep public renderer API unchanged
8. Verify Android and JVM compilation plus tests
